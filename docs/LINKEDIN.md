# LinkedIn: как берутся описания вакансий и почему так

Письма LinkedIn job alerts дают только должность, компанию и номер вакансии. Описание нужно для оценки.
Главное требование (решение пользователя 01.11.2026): **LinkedIn ни при каких условиях не должен связать эти
запросы с аккаунтом пользователя**. На втором месте — стабильность и простота поддержки.

**По умолчанию работает только Google for Jobs:** запасной путь через публичные страницы выключен в коде, в конфиге и на
экране (`LinkedInPublicPages.enabled = False`, `mail.yaml`, Settings → *LinkedIn pages (proxy)*), прокси пока не куплен.

Замки, все проверены `tests/test_linkedin_off.py`:
- кнопка Save настроек до переключателя не достаёт, у него свои два адреса;
- включить можно только при заданном прокси, прошедшем проверку прямо сейчас, и с набранной вручную фразой;
- выключить можно всегда, без сети; переключатель перечитывается перед каждой страницей, идущий прогон останавливается;
- опции «без выхода» больше нет; у клиента нет прямого маршрута: без запущенного выхода он не создаётся, его единственный
  транспорт — прокси, системные и переменные окружения игнорируются (`trust_env=False`), сбой прокси не откатывается на прямое соединение;
- перед каждой страницей выход проверяется; домашний адрес через прокси приравнен к отсутствию прокси.

Схема ниже — как он устроен, когда включён.

## Схема

```
письмо LinkedIn ─► Google for Jobs (JSearch → SerpApi)        ноль запросов к LinkedIn
                     │ нашёл ─► описание, вакансия сразу в ленте
                     │ не нашёл
                     ▼
                   ждёт (raw status waiting_page, в ленте её нет)
                     │ не раньше чем через delay_days (1 день)
                     ▼
                   публичная страница LinkedIn через приватный выход (collectors/linkedin_guest.py)
                     │ нашёл ─► описание (+ ссылка Apply на сайт работодателя, если есть)
                     │ нет страницы / прошло max_wait_days (3 дня) ─► оценка по письму («E-mail only»)
                     ▼
                   лента
```

В ленте только вакансии, для которых описание нашёл Google, нашла страница LinkedIn, или не нашёл никто.
Statistics → Sources у почтового ящика показывает доли: Google for Jobs / LinkedIn page / Not found / Waiting.

## Почему не библиотека

Ресёрч 01.11.2026 (GitHub, PyPI, Issues, Reddit, HN, блоги):

- **JobSpy** (`python-jobspy`, ~4,6 тыс. ★, жива) — единственная популярная библиотека без входа. Но описание
  по номеру вакансии у неё — приватная функция внутри поиска, а по сети она рискованнее нашего клиента:
  выполняет редиректы (и принимает cookies в цепочке до `/authwall`), пауза 3–7 с, нет остановки после отказа.
- `linkedin-api` (tomquirk), `py-linkedin-jobs-scraper` (spinlud), `linkedin_scraper` и подобные работают **под
  аккаунтом** (`li_at`, вход, профиль Chrome) — прямой путь к ограничению аккаунта. Не использовать никогда.

Поэтому — свой минимальный клиент: всё, что держит запросы анонимными, в одном файле и покрыто тестами.

## Чем LinkedIn мог бы связать запросы с аккаунтом и что с этим сделано

| Канал | Что сделано |
|---|---|
| **Общий IP.** Аккаунт открыт в браузере на этом же Mac и в той же Wi‑Fi — анонимный запрос с домашнего IP связан с аккаунтом напрямую | Запросы к LinkedIn идут **только** через приватный выход (прокси) и никогда напрямую. Перед **каждой** страницей: выход отвечает, его IPv4 ≠ домашний IPv4, его IPv6 вне домашней сети /64, адрес не сменился за прогон. Любой сбой — LinkedIn в этом прогоне не открывается вовсе |
| **Выход, которым пользуется человек.** Тот же VPN-сервер, что у пользователя в телефоне | Выход — отдельный прокси только для приложения. Это не системный VPN: его не включить для всего Mac или браузера, другие вкладки и программы его не используют (он задан только в HTTP-клиенте этого загрузчика) |
| **Cookies** (`bcookie`, `bscookie`, `lidc`, `JSESSIONID`, `li_gc`) | Не принимаются и не отправляются (cookie jar, который отклоняет всё), между запусками ничего не хранится |
| **Редиректы, Referer** | Редиректы не выполняются (редирект = отказ = пауза), Referer не отправляется |
| **Ссылки и пиксели в письмах.** В ссылках из писем — токены входа (`midToken`, `otpToken`), пиксель `/emimp/` сообщает об открытии письма | Адрес страницы собирается **только** из номера вакансии. Письма читаются через IMAP `BODY.PEEK`, картинки и ссылки не загружаются никогда |
| **Набор номеров.** Анонимный клиент спрашивает ровно те вакансии, что пришли одному аккаунту | Спрашиваются только промахи Google for Jobs (около трети), не раньше чем через день после письма, не больше `max_per_day` в день |
| **Браузерный отпечаток, WebRTC, DNS** | Браузер не запускается никогда (только HTTP-клиент). Прокси — HTTP CONNECT: имя резолвит прокси, DNS не утекает |
| **Ссылка Apply** на сайт работодателя | Только читается со страницы и пишется в описание («Apply: …»), приложение её не открывает |

Случаев ограничения **аккаунта** из-за запросов без входа (с другого IP) в открытых источниках не нашлось;
у всех без входа худший исход — блокировка IP. Но политика LinkedIn прямо говорит, что IP и данные устройства
используются для связывания, — поэтому общий IP закрыт жёстко, а не «скорее всего не заметят».

## Отказы LinkedIn

Первый 429 / 999 / 401 / 403 / любой редирект / стена входа / капча — пауза на `pause_days` (2 дня), без повторов,
без смены выхода. Вакансии ждут; через `max_wait_days` оцениваются по письму. 27.10.2026 сервер коммерческого VPN
получил 429 на третьей странице: такие серверы — датацентровые IP, общие с тысячами людей, LinkedIn режет их первыми.
Поэтому выход по умолчанию — **резидентный** прокси.

## Настройка выхода (один раз)

1. Резидентный прокси с оплатой за трафик, который не сгорает. Например, DataImpulse (≈ $1 за ГБ, минимум $5 —
   цены на 01.11.2026 по обзорам, проверить на сайте). Страница вакансии — сотни килобайт; 12 страниц в день —
   десятки мегабайт в месяц, $5 хватит очень надолго.
2. В кабинете прокси включить **sticky session** (один IP на время прогона, обычно 10–30 минут) и, если можно,
   страну — Сербия. Без sticky session проверка «адрес не сменился» остановит чтение на второй странице.
3. `config/.env`: `LINKEDIN_PROXY_URL=http://логин:пароль@хост:порт` (только `http://` / `https://`).
4. Проверка без единого запроса к LinkedIn:
   ```bash
   .venv/bin/vacancy-retriever linkedin-exit
   ```
   Должно быть `OK: …`. Иначе причина — что именно не так.
5. Settings → *LinkedIn pages (proxy)*: набрать фразу и нажать *Check the proxy and turn on*.

Запасной вариант выхода — свой VLESS-сервер через Xray (`exit.kind: vpn`), с теми же проверками.

## Что никогда не делать

Входить в LinkedIn из приложения, использовать `li_at` или профиль Chrome пользователя, запускать браузер,
открывать ссылки и картинки из писем, ходить в поиск или профили, открывать LinkedIn с домашнего IP, автоматически
менять выход или сервер после отказа, повторять запрос после отказа.
